## Research question and next step

What should an early portfolio demonstrate for customer-facing AI delivery, and how would that evidence differ for applied AI research? The OpenAI and Mayo Clinic descriptions support a provisional focus on reliable workflows and explicit handoffs. Amazon's applied-science role suggests an alternative focused on reproducible experiments and failure analysis. The sample is limited to three examples of experienced roles.

Next, test a public-information workflow with a manual lookup baseline and 10 synthetic cases. Expect official sources for seven supported answers and a human-review handoff for three unsupported inputs. Record expected and observed results. This check is planned.

## Reader and portfolio design

The primary reader is a technical hiring manager scanning for evidence of what the student built and how it was checked. A recruiter would prioritize a concise skills summary. The portfolio will emphasize the manager’s need to open code and verification quickly.

**Portfolio promise** · For a technical hiring manager, this portfolio makes it easy to see the problem, my contribution, and the evidence, then open the strongest case study.

| Concept | Voice and character | Layout and reference |
| --- | --- | --- |
| Evidence-first portfolio | Precise, practical, candid. Guide archetype. | Use an orderly grid, constrained reading width and source links next to each claim. Stack cards in one column on small screens. [GOV.UK Design System layout](https://design-system.service.gov.uk/styles/layout/) |
| Annotated field notebook | Curious, direct, reflective. Explorer archetype. | Place dated observations and decision notes beside project entries. Stack annotations after their entries on small screens. [Smithsonian field book example](https://naturalhistory.si.edu/education/teaching-resources/life-science/field-book-activity-making-and-recording-observations) |

Both concepts use the same introduction, project stories and **Inspect project evidence** action. The first is the provisional choice because a predictable path from claim to source should make short review sessions easier. The notebook gives more space to explain how decisions changed but adds detail to scan. A partner can test that tradeoff.

Two reasons to trust the work are inspectable artifacts and a candid account of one limitation. A repository and repeatable check support the specific behavior shown. A limitation helps the reviewer judge how far the example transfers to another problem.

## Visitor stories and planned acceptance checks

| --- | --- |
| As a technical hiring manager, I want to find one relevant project so I can judge how the student approaches a user need. | From the landing page, find a case study and explain its user and problem. |
| As a reviewer, I want to see the student’s contribution so I can judge it fairly. | Point to what the student built, what teammates or starter code supplied, and one limit. |
| As a reviewer, I want to inspect a check so I can trust a specific behavior. | Open the linked source and check. Identify the expected result and whether it was observed. |
| As a keyboard or phone visitor, I want to reach the evidence without getting stuck. | Use the project navigation and evidence links with visible focus and readable text at a narrow viewport. |
